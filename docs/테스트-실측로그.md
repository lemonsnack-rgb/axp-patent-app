### 산술 정합성 검증 (강한 판정 근거)

- NOT 정합: `하이브리드`(16,607) − `하이브리드 and 자동차`(1,684) = **14,923** = `하이브리드 not 자동차` 실측값. 정확히 일치 → AND/NOT 연산 정합.
- OR 확장: `or`(173,413) > 각 단독어(16,607 / 158,490) → 정합.
- 범위코드 단조 확장: `KEY`(158,490) < `TAC`(168,578) < `DSC`(383,150) → 규약상 KEY⊂TAC⊂DSC 포함관계와 정합.
- 필드절 해석 확인: `KEY:(자동차)` = `자동차` 단독(158,490)이나 `TAC:(자동차)`는 다른 값 → 필드절이 문자열로 무시되지 않고 **실제 해석됨**. 기본 검색어 범위가 `명칭+요약+독립항`(KEY)이라 KEY와 단독어가 같은 것도 정합.

### 특수문자 검증 범위 (정정)

- 따옴표 `"` → V2 표시 + 버튼 disabled
- `@#$%` → 검증 통과, 검색 실행(0건)
→ V2는 특수문자 전반이 아니라 **특정 문자(따옴표 등)** 에만 반응하는 것으로 관측. D4 후보 보강.

### URL 인코딩 확인 (결함 아님으로 확정)

- `@#$%` 검색 직후 `location.href` 는 `?query=@#$%` (미인코딩 표시)
- 새로고침 후 `?query=@%23$%25` 로 정규화, 검색식 `@#$%` 입력창 복원, `0건` 결과 유지
→ 기능 손실 없음. 결함 아님.

### 검색식 미확인 (잔여)

- 공백만 입력
- 일자 범위 표기 `CODE:([from ~ to])`
- 필드절 + 연산자 조합 (예: `KEY:(자동차) and TAC:(수소)`)
- 매우 긴 검색식 (길이 상한)
- `NPCT` 등 개별 필드코드

#### D4/BUG-004 원인 정정

- 앞서 "V2는 특수문자 전반이 아니라 특정 문자에만 반응" 이라 기재했으나 더 정확히는:
  **V2는 따옴표 `짝 불일치` 에 반응한다.** 짝이 맞으면 통과하고 정확구 검색이 동작한다.
- 따라서 결함의 정확한 내용은 **문구-원인 불일치**다:
  - 따옴표 짝 불일치(`"하이브리드 자동차`) → V2 `검색어에 사용할 수 없는 문자가 있어요. 특수문자를 확인해주세요.`
  - 그런데 V1 `검색식 형식이 올바르지 않습니다. 괄호·연산자(AND·OR·NOT)·따옴표 짝을 확인해주세요.` 가 `따옴표 짝` 을 담당한다고 서술
  - 즉 따옴표 짝 오류가 V1이 아니라 V2로 분기되어, 안내 문구로 원인을 특정할 수 없다
- `@#$%` 통과는 별개 사안: 특수문자만으로 이루어진 무의미 검색식이 실행되어 0건 반환 (별도 후보 유지)

- `등록` 체크 후 `적용` → URL `fk_statuses=등록`, `725건`, 상태 컬럼 전 행 `등록`, 필터 버튼 라벨에 선택 수 `1` 표시. **정상**

#### BUG-026 정정 — 결함 아님

- 좌측 `권리상태` 패싯에 **`공개` 가 유효한 값으로 존재**한다(180건)
- 따라서 결과 표 `상태` 컬럼에 `공개` 가 나오는 것은 정상이다
- 앞서 `확인 필요` 로 둔 BUG-026 은 **결함 아님**으로 정정한다

#### 신규 관측 — 상단 `상태` 필터와 좌측 `권리상태` 패싯의 값 집합이 다르다

| 위치 | 값 |
|---|---|
| 상단 `상태` (검색 입력) | `출원` `심사중` `등록` `거절` `소멸` `취하` `포기` `무효` (8) |
| 좌측 `권리상태` (결과 패싯) | `등록` `소멸` `거절` `공개` `취하` `포기` (6) |

- 상단에는 `공개` 가 없고, 좌측에는 `출원`·`심사중`·`무효` 가 없다
- D29 후보 (확인 필요) — 두 필터의 값 체계가 일치하지 않아 사용자가 같은 축으로 오인할 수 있다

#### BUG-024 강화 — `IPC` 컬럼 미표시는 데이터 부재가 아니다

- 좌측 `IPC` 패싯에는 `G06Q-050/26 (82건)` 등 **IPC 값이 20종 존재**한다

## 오류 화면 · `새 탭에서 열기` · `탭 닫기`

### 존재하지 않는 키 진입 시 오류 화면 — 정상

| 진입 URL | 표시 |
|---|---|
| `/patent-front/patents/9999999999999` | `role="alert"` — **`특허를 불러오지 못했습니다.\n새로고침 후(F5) 다시 시도해 주세요.`** |
| `/patent-front/papers/00000000-0000-0000-0000-000000000000` | `role="alert"` — **`논문을 불러오지 못했습니다.\n새로고침 후(F5) 다시 시도해 주세요.`** |

- 두 화면 모두 상단 `탭 닫기` + 푸터만 남고 본문은 렌더되지 않음 (특허 오류 화면 본문 길이 451자)
- 도메인별로 문구가 구분됨(`특허를`/`논문을`) — 정상
- 오류 문구 목록(원문 4종): V1·V2(검색식 검증), V3 `검색에 실패했습니다.…`, 그리고 위 상세 로딩 실패 2종

### `새 탭에서 열기` — 정상

- 요소: `link "새 탭에서 열기"`, `target="_blank"`, **`rel="opener"`**
- href: `/patent-front/papers/<uuid>?query=…` (검색어 파라미터 유지)
- 실제 클릭 → 새 탭이 열리고 논문 상세가 정상 렌더됨
- `rel="opener"` 는 `noopener` 가 아니라 opener 를 **유지**한다. 같은 오리진 내부 링크이며,
  아래 `탭 닫기` 가 동작하기 위한 조건이다(브라우저는 스크립트로 열리지 않은 탭의 `window.close()` 를 차단)

### `탭 닫기` — 정상 (조건부 동작이며 fallback 도 적절)

| 진입 경로 | `탭 닫기` 클릭 결과 |
|---|---|
| `새 탭에서 열기` 로 열린 탭 | **탭이 실제로 닫힘** (디버깅 대상 소멸, `list_pages` 에서 사라짐) |
| 주소창 직접 진입(opener 없음) | 탭이 닫히지 않고 목록(`/patent-front/papers`)으로 이동 |

- 순회 초기에 직접 URL 진입 상태에서 관측해 "라벨과 동작 불일치" 로 볼 수 있었으나,
  의도된 경로에서는 정상 동작하며 opener 가 없을 때만 목록으로 되돌아가는 **fallback** 이다
- 판정: **결함 아님**
- 테스트 주의사항: `탭 닫기` 는 진입 경로에 따라 동작이 다르다. 반드시 `새 탭에서 열기` 로 열린 탭에서 검증해야 한다

#### D40 (중대) — `인용` 과 `피인용` 의 내용이 동일

- 두 섹션의 건수(2건)와 문헌번호 목록이 완전히 동일하다
- 인용(backward, 이 특허가 인용한 문헌)과 피인용(forward, 이 특허를 인용한 문헌)은 서로 다른 집합이어야 한다
- 설계 `PAT-DET` 계열 명세에서도 인용/피인용을 구분한다(`citation.std_citation_*` vs 피인용)
- BUG-004(`출원`≡`심사중`)와 같은 유형의 문제
