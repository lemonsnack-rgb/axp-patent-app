# 0. 먼저 읽을 것 — 배경 지식

A-1을 **이해하고** 고치려면 이 네 가지를 알아야 한다. 코드만 복사하면 다음에 비슷한 값이 들어왔을 때 또 틀린다.

## 0-1. 「공개」와 「공고」는 다른 사건이다

특허 하나는 살면서 공보(공식 문서)를 **여러 번** 낸다.

```
출원 ──1년 6개월──▶ 공개공보          ──심사──▶ 등록 ──▶ 등록공고공보
                    "이런 출원이 있다"           "심사를 통과했다"
                    공개번호 + 공개일             공고번호 + 공고일
```

- **공개**는 심사 결과와 무관하게 시간이 되면 자동으로 난다. **등록보다 항상 앞선다.**
- **공고**는 등록이 결정된 뒤에 난다. **등록보다 항상 뒤다.**
- 그래서 **한 화면에 번호 2개·일자 2개**가 나올 수 있고, 서로 짝이 정해져 있다.
- 조기 등록되면 공개공보가 **아예 없다**(우리 데이터 392건). 결손이 아니라 정상이다.

**PCT(국제출원) 국내단계**는 여기에 한 단계가 더 붙는다.

```
국제출원 ──▶ 국제공개(WO 번호)  ──국내 진입──▶ 국내 공개(번역문)  ──▶ 등록 ──▶ 등록공고
             예: WO 2011/146808              예: 2022-07-26
             2011-11-24
```

`KR 10-2635013 B1`이 이 경우다. **국제공개일(2011)과 국내 공개일(2022)은 11년 차이가 난다.** 둘을 섞으면 안 된다.

## 0-2. 우리 데이터가 이 값을 어디에 담는가

API 응답(`GET /api/service/axp/patent-searches/{문헌번호}`)의 `meta_json.bibliographic` 안에 있다.

| 필드 | 담긴 값 | 채움률 | 주의 |
|---|---|---|---|
| `publication_number` | 공개번호 **또는** 공고번호 **또는** 국제공개번호 | 78% | **한 필드에 3계열이 섞여 있다** → 형식으로 구분 |
| `publication_date` | 공고일이 **대부분**이지만 국제공개일·공개일도 섞여 있다 | 100% | **이름만 믿으면 안 된다** ← A-1·A-2의 원인 |
| `open_date` | 공개일(국내) | 72% | 없으면 공개공보가 없던 문헌 |
| `register_date` | 등록일 | 100% | 공고일 판정의 기준선 |
| `register_number` | 등록번호 | 100% | 공고계 번호와 값이 같다 |

즉 **필드 이름과 실제 값이 1:1이 아니다.** 그래서 "번호 형식"과 "일자 논리"를 함께 봐야 한다.

## 0-3. 이번 오류가 나온 경위

1차 지시서에 내가 **「번호 형식만 보고 짝 일자를 정하라」**고 적었고, `publication_date`를 항상 공고일로 전제했다. 데이터에는 그 전제를 깨는 값이 **115건**(WO 113 + 실용신안 2) 있었다. 개발은 지시대로 구현했으므로 **코드 잘못이 아니라 규칙 잘못**이다.

더 근본 원인은 **한 칸(문헌번호 행 우측)에 여러 의미를 담은 레이아웃**이다. 그래서 이번에는 라벨을 바꾸는 대신 **계열마다 행을 나눈다**(§A-1). 라벨이 고정되면 판정이 「어느 행에 넣을까」 하나로 줄고, 새 데이터가 들어와도 규칙이 흔들리지 않는다.

## 0-4. 판정 로직을 어디에 둘 것인가

권장: **한 곳에서만 판정하고 결과를 넘긴다.**

| 방식 | 장단 |
|---|---|
| 서버(API)에서 판정해 라벨·값을 내려줌 | 화면이 여러 개(상세·검색결과·리포트)여도 규칙이 하나. **권장** |
| 프런트 공통 함수 | 서버 변경이 어려우면 차선. 단, 같은 함수를 모든 화면이 import 할 것 |

**하지 말 것**: 상세페이지 컴포넌트 안에 `if`로 흩어 놓기. 다음에 공개 문헌이 적재되면 같은 버그가 화면마다 재발한다.
참고 구현: 목업 `src/components/patentDetailRules.ts` (순수 함수 + 회귀 테스트).

# A. 지금 수정 (3건)

## A-1. 공개·국제공개·공고를 **항목 고정 + 값 배치 정정** — 115건 수정 · 전건 구조 변경

### 무엇이 문제인가

`문헌번호` 행의 우측 칸이 **상황에 따라 다른 의미**를 갖는다. 그래서 아래 두 유형이 틀렸다.

```
현재 ①  문헌번호  10-2620084 B1   공고일   2024-01-02        ← 여기까진 맞다
     ②  문헌번호  10-2635013 B1   공고일   2011-11-24        ← 등록일(2024-02-05)보다 13년 앞선다
        국제공개번호 WO 2011/146808 공개일  2022-07-26        ← 번호와 계열이 다르다      113건
     ③  문헌번호  20-0497874 Y1   공고일   2023-04-05        ← 등록일(2024-03-18)보다 앞선다  2건
        공개번호  20-2023-0000689  공개일  (빈칸)
```

한 칸이 세 얼굴을 가지니 판정이 복잡해지고, 새 데이터가 들어올 때마다 어긋난다.

### 수정 방향 — 계열마다 항목을 따로 두고, 항목은 고정한다

**라벨 6개(공개번호·공개일·국제공개번호·국제공개일·공고번호·공고일)를 고정 노출**하고, 값이 없으면 `—` 로 둔다(§B-2 결정).
한 칸이 상황에 따라 다른 의미를 갖지 않으므로 판정은 **「값을 어느 칸에 넣을까」** 하나로 줄어든다.

```
문헌번호      10-2635013 B1     문헌종류     등록특허공보
출원번호      10-2022-7017111   출원일       2011-05-20
공개번호      —                 공개일       2022-07-26     ← 국내 공개(번역문)
국제공개번호   WO 2011/146808    국제공개일    2011-11-24     ← 국제공개
공고번호      —                 공고일       —              ← 이 문헌엔 공고 데이터가 없다
등록번호      10-2635013        등록일       2024-02-05
```

**항목은 전 문헌 고정**이다. 값이 없으면 `—` 로 두고 라벨을 지우지 않는다.

| 칸 | 값 |
|---|---|
| `공개번호` | `publication_number` 가 `10-YYYY-NNNNNNN` 형식일 때 |
| `공개일` | `open_date` · 없고 `publication_date` 가 공고일도 국제공개일도 아니면 그 값 |
| `국제공개번호` | `publication_number` 가 `WO YYYY/NNNNNN` 형식일 때 |
| `국제공개일` | 위와 같을 때의 `publication_date` |
| `공고번호` | `publication_number` 가 `10-NNNNNNN` 형식일 때(= `register_number` 와 동일) |
| `공고일` | `publication_date >= register_date` 일 때만 |

### 판정 로직 (단순해진다)

항목이 고정이므로 남는 판단은 **「publication_date 를 어느 칸에 넣을까」** 하나뿐이다.

```ts
const isYmd = s => !!s && /^\d{4}-\d{2}-\d{2}$/.test(s);
// 공고는 등록 이후에 나온다. 등록일이 없거나 '-'·'—' 면 비교하지 말 것(문자열 비교가 잘못 통과한다).
const isBulletin = isYmd(pubDate) && isYmd(regDate) && pubDate >= regDate;

const isWo     = /^WO \d{4}\/\d{6}$/.test(pubNo);
const isOpenNo = /^\d{2}-\d{4}-\d{7}$/.test(pubNo);
const isRegNo  = /^\d{2}-\d{7}$/.test(pubNo);

return {
  공개번호:     isOpenNo ? pubNo : '',
  // publication_date 가 공고일도 국제공개일도 아니면 공개일이다(open_date 결손 보완 · 2건)
  공개일:       openDate || (!isBulletin && !isWo && pubDate ? pubDate : ''),
  국제공개번호: isWo ? pubNo : '',
  국제공개일:   isWo ? pubDate : '',
  공고번호:     isRegNo ? pubNo : '',
  공고일:       isBulletin ? pubDate : '',
};
// 화면에서는 빈 문자열을 '—' 로 표시한다(§B-2). 항목을 숨기지 않는다.
```

이전 안(칸 재사용)에 필요했던 **9행짜리 결정표가 사라진다.**

> **국가별 번호 형식 주의** — 위 정규식은 **KR 형식만** 판정한다(현재 적재분 전건 KR). 해외 문헌이 적재되면 `US 2025/0098006 A1`·`JP 2020-533798 A`·`CN 107665952 A`·`EP 3276698 B1` 같은 형식이 들어와 **공개번호 칸이 비게 된다.** 해외 적재 전에 형식 목록을 확장할 것.

### 실데이터 분포 — 어떤 행이 몇 건에 나오는가

| 나오는 행 | 문헌 수 | 예시 |
|---|---|---|
| 공개 + 공고 | **1,198** | `KR 10-2620084 B1` · `KR 10-2649868 B1` |
| 공고만 | **491** | `KR 10-2618432 B1`(공개 없이 등록) |
| 공개 + 국제공개 | **112** | `KR 10-2635013 B1` |
| 공개만 | **2** | `KR 20-0497874 Y1`(공고일 없음) |
| 국제공개만 | **1** | 국내 공개일 결손 |
| **합계** | **1,804** | 3행이 필요한 문헌은 없다 |

### 개발자용 단위 테스트 케이스

실제 문헌 값이다. 입력 `(pubNo, pubDate, openDate, regDate)` → 기대 행 배열.

| 입력 `(pubNo, pubDate, openDate, regDate)` | 기대 (빈 값은 화면에서 `—`) | 출처 |
|---|---|---|
| `('10-2018-0013604','2024-01-02','2018-02-07','2023-12-27')` | 공개번호 `10-2018-0013604` · 공개일 `2018-02-07` · 공고일 `2024-01-02` | `KR 10-2620084 B1` |
| `('WO 2011/146808','2011-11-24','2022-07-26','2024-02-05')` | 공개일 `2022-07-26` · 국제공개번호 `WO 2011/146808` · 국제공개일 `2011-11-24` · **공고일 빈값** | `KR 10-2635013 B1` |
| `('20-2023-0000689','2023-04-05',undefined,'2024-03-18')` | 공개번호 `20-2023-0000689` · 공개일 `2023-04-05` · **공고일 빈값** | `KR 20-0497874 Y1` |
| `('10-2649868','2024-03-20','2023-03-07','2024-03-18')` | 공개일 `2023-03-07` · 공고번호 `10-2649868` · 공고일 `2024-03-20` | `KR 10-2649868 B1` |
| `('','2024-01-02',undefined,'2023-12-21')` | 공고일 `2024-01-02` · 나머지 빈값 | `KR 10-2618432 B1` |
| `('US 2025/0098006 A1','2025-10-12','2024-03-09','-')` | 공개일 `2024-03-09` · **공고일 빈값** | **미등록 문헌 가드** |

마지막 줄이 중요하다. 등록일이 `'-'`·`'—'` 같은 자리표시자면 **문자열 비교가 잘못 통과한다**(`'2025-10-12' >= '-'` 는 참). 반드시 `YYYY-MM-DD` 형식을 먼저 확인한다.

### 함께 정리되는 것

- **「문헌일」 라벨은 없앤다.** 그 값(`open_date`)은 이제 `공개일` 행으로 간다
- `문헌번호` 행 우측이 비므로 **`문헌종류`를 그 자리로 올린다**(기존 `문헌종류|권리상태` 행은 `권리상태`가 좌측으로)
- 목업은 이 구조로 이미 수정했다 — `src/components/patentDetailRules.ts` 의 `pubRows()` 와 회귀 테스트 8종 참고

## A-3. 국가 R&D 정보 블록 제거 — 전건

**위치** `#etc` 기타정보 안 「국가 R&D 정보」 블록

# B. 결정 사항 — B-1 대기 · B-2 확정

## B-1. 삭제된 청구항 처리 — **변리사 확인 후 결정**

**위치** `#claims` → 항 라벨(`독립항 — 제N항` / `종속항 (제N항 → 제M항 인용)`)과 본문, 상단 토글 `독립항`·`전체청구항`

**확정 사실** (안 선택과 무관)

- 심사 중 취하돼 본문이 **「삭제」 한 단어**인 항이 **4,323개**(1,237문헌·68%)
- 이 항들은 **전건 `depends_on`이 없어** 현재 규칙에서 **「독립항」으로 분류**된다
- 서지 「청구항 수」(=`claim_count`, 삭제 제외 실질 수)와 목록 개수가 어긋나 보인다 — 1,245문헌
- 「독립항/전체청구항」 토글이 **같은 결과**를 내는 문헌이 309개

**물어야 할 것**

1. 삭제항을 목록에서 **빼는 게 맞는가**, 「삭제」로 **남기는 게 맞는가**
2. 남긴다면 **독립항 분류에서만 빼면 되는가**
3. 서지 「청구항 수」와 목록 개수를 **어느 기준으로 맞출 것인가**

| 안 | 목록 | 독립항 토글 | 서지 숫자와 |
|---|---|---|---|
| A | 삭제항 제외 + 「삭제된 청구항 N개」 접기 | 실질 독립항만 | 일치 |
| B | 「삭제」 라벨로 목록에 남김 | 독립항 분류에서 제외 | 불일치 |
| C (현행) | 전부 노출 | 삭제항이 독립항으로 표시 | 불일치 |

```ts
const isDeleted = t => /^\s*삭제\s*\.?\s*$/.test(t);   // 판별식은 어느 안이든 동일
```

**현재 상태** `KR 10-2620415 B1` 독립항 46개 중 **45개가 「삭제」**·서지 `1개` / `KR 10-2635013 B1` 삭제 64개·서지 `18개` / `KR 10-2619202 B1` 독립항 8개 중 2개

## B-2. 비어 있는 항목의 표시 방식 — ✅ **결정됨: 라벨 유지**

> **채움률 0%는 「불필요」가 아니다.** 지금 적재분이 KR 등록건뿐이라 비어 있을 뿐, 앞으로 값이 들어올 수 있다.

**결정**: **항목(라벨)은 항상 고정 노출하고, 값이 없으면 `—` 로 표시한다.** 숨기지 않는다.

- 항목이 화면에서 사라지면 **사용자가 그 항목의 존재 자체를 모른다.**
- 항목이 문헌마다 나타났다 사라지면 **표가 들쭉날쭉해 오류처럼 보인다.**
- 값이 들어오면 `—` 가 값으로 바뀌기만 하면 된다 — 별도 작업이 필요 없다.

**적용 대상** (현재 전건 `—` 로 나오는 항목)

| 화면 | 라벨 | 필드 |
|---|---|---|
| `#bibliographic` | 최종처분상태 | `final_disposal` |
| `#bibliographic` | 출원구분 | `application_flag` |
| `#bibliographic` | 실시권 등록일 | `license_registration_date` |
| `#bibliographic` | 지정국 | `designated_country` |
| `#bibliographic` | 권리변동 | 이력 유무로 판정(§E-4) — 이력 없으면 `—` |

**주의** — 「값이 없으면 라벨 칸까지 비운다」는 이전 지시(1차 §5)는 **폐기**한다. 그 결과로 서지 표 마지막 행이 3칸이 되거나 표 중간에 구멍이 생겼다.

```
○  최종처분상태  —          출원구분  —
✗  (빈)         (빈)        출원구분  —
✗  행 자체를 없앰
```

# F. 재발 방지 규칙

지금까지 나온 오류는 **데이터 상태를 가정하고 라벨을 붙인 것**이 원인이다.

**① 일자 논리 검증** — 라벨을 붙이기 전에 확인한다.

```
공고일  ≥ 등록일        (공고는 등록 이후)
공개일  ≤ 등록일        (공개는 등록 이전)
국제공개일 ≤ 국내 공개일
```
조건을 어기는 값은 **라벨을 붙이지 말고 로그로 남긴다.**

**② 일자 비교 전 형식 검증 필수** — 현재 적재분은 전건 등록이라 드러나지 않지만, 공개 단계 문헌이 들어오면 등록일이 없다. `'2025-10-12' >= '-'` 는 문자열 비교에서 **참**이 되어 공개일을 공고일로 표기한다. 반드시 `YYYY-MM-DD` 형식을 확인한 뒤 비교한다.

**③ 코드 값은 그대로 노출하지 않는다** — 단, 관측되지 않은 코드는 **추정 매핑하지 말고** 원값을 남긴다.

**④ 판정 규칙은 적재 범위와 함께 넓힌다** — 번호 형식·코드 도메인·일자 논리는 모두 **현재 적재분(KR 등록 1,804건)** 을 보고 만든 것이다. 공개 문헌·해외 문헌이 들어오면 ①②③이 그대로 통하지 않는다. 적재 범위가 바뀔 때 이 문서의 규칙을 함께 점검한다.

**⑤ 「값이 없다」를 세 가지로 구분한다** — 미반입(도면·원문) / 정상 부재(공개 없이 등록) / 결손(적재 오류) / *그리고 필드 자체가 없는 것*(국가 R&D). 처리 방식이 각각 다르다.
